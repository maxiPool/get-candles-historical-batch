## What was wrong
- Since 12 Aug the June-27 jar wrote into an empty `~/Documents/all_candles/candles-monthly`. The folder had been
  emptied, and the jar's lock-file code recreated it with `mkdirs`. It seeded 5000 candles per pair under
  `SYM_TF_YYYY_MM.csv`.
- From 13 Aug its finder (`-YYYY_MM.csv` only) matched 0 files, did nothing and logged success.
- The fix 6eee6d8 was committed but never deployed. Nothing checked that the jar matched the source.
- Master `/home/max/data/documents/all_candles/candles-monthly` ends 2026-08-12 ~20:59Z.

## What changed
- Output is the master folder, set on `infra.oanda.v20.data-root`. The local profile still overrides
  `infra.oanda.v20.base` to `~/Documents`, but nothing reads `base` now. The data folder is never created.
- The download is chunked from/to (4500 granules per request), with 4 attempts and backoff, and a 20 ms
  global throttle. The silent count fallback is gone. Rows are deduplicated by time on append.
- Each run fails loudly (log + one email + exit 1) on: 0 matched files, more than 4 pairs without a file,
  a failed download, a missing or empty data folder, 0 new candles on a weekday, stale data
  (> 24 market hours after the run), a stale jar (the jar's build commit differs from HEAD in `src/` or
  `pom.xml`), and an unexpected exception.
- Watchdog: `bin/cron-wrapper.sh` emails on any non-zero exit, so alerts still go out when Java can't start.
  `bin/freshness-check.py` runs daily and emails after 2 weekdays without a successful run. It reads
  `last-success.txt`, which only full runs write.
- `bin/deploy.sh` builds from a clean HEAD with the tests, embeds the commit, keeps the previous jar as
  `deployment/previous-*.jar` and writes `deployment/DEPLOYED`.
